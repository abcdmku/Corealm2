**Performance audit — 6 September 2026**

The 256-player display cap bounds actor presentation, but the crowded production scene still has a 33 ms median frame interval on an RTX 5080 at reduced settings, delivering roughly 26 to 29 frames per second over the sampled windows. Rendering is the largest measured client cost. Startup and server replication also need work before the proposed 1,000-player performance targets can be accepted.

This audit changes no gameplay or rendering behavior. It adds a repeatable [audit tool](../../tools/multiplayer-perf-audit.ts). Run `npx tsx tools/multiplayer-perf-audit.ts --production` after `npm run build`; omit `--production` for readable development CPU profiles. A tool result of `passed: true` checks actor selection and uncaught page errors, **not** a performance target.

**Client measurements**

Fresh Chromium context, production Vite preview, local loopback, Intel Core Ultra 9 285K, RTX 5080 through ANGLE/D3D11, approximately 95.5 GiB system RAM. Viewport 1280 × 800, render scale 0.7, low shadows, near draw distance. No network or CPU throttling. The fixture uses the authored production scene, one actual network/browser client and 999 moving server fixture actors. It does not represent 1,000 network clients.

A second production run confirmed median 33.3 ms and p95 50.1 ms in the crowd, versus 16.7 ms for both empty-scene percentiles. Crowd frame counts after discarding the first three intervals were 436 and 386 across the two 15-second windows; reciprocal median interval is not average delivered FPS. Draw calls in the repeat ended at 1,759 with 20.51 million triangles.

The selected count comes from the distance filter, not an independent count of completed GPU draws. The crowded screenshot was inspected and shows the production avatars and connected UI. Resource counts alone do not establish a memory leak. The debug heap estimate is coarse and was not used to diagnose retention.

**Findings, in implementation priority order**

1. **High: crowded rendering consumes most of the client frame budget.** The crowded window records 1,231 more draw calls and 11.78 million more triangles than the earlier empty window. Ongoing world streaming may contribute to this difference, so it is not an isolated per-avatar cost. In the first production crowd CPU sample, the renderer accounts for 57.9% of sampled wall time, including about 16.2% under shadow rendering. These are overlapping inclusive stack percentages, not additive costs or GPU timings. The readable source run corroborates the result: renderer 55.5%, shadow pass 15.0%, with substantial Three.js geometry-attribute updates, material/program selection and scene traversal. See [renderer](../../game/src/render/renderer.ts), [actor views](../../game/src/render/entityViews.ts), and [aggregated source stacks](../../test-results/performance-audit/source/crowd-stacks.json). Investigate shared geometry/material batches, rig and palette representation, shadow caster workload and unnecessary attribute updates first. Preserve required character detail and animation. Measure each change in the same scene; a lower resolution alone will not remove CPU submission and traversal costs. This audit does not establish whether GPU execution is also limiting frames.

2. **High: the retained 1,000-client runs miss both server latency targets.** These are existing sustained runs from earlier implementation fingerprints, reviewed here rather than rerun against the current build. Both used 1,000 active network clients for ten minutes with movement and production mining, plus churn, slow consumers and a rejected 1,001st admission. Distributed placement measured p95 tick **125.2 ms** and acknowledgement **362.0 ms**; clustered placement measured **199.7 ms** and **748.7 ms**. Targets remain below 100 ms and 250 ms respectively. Clustered replication accounts for about 69% of recorded stage time and delivers about **18.3 MB/s aggregate** to the clients. The client-only 256 cap leaves server interest at 48 metres, so this fan-out is unchanged. Prioritize reusable public encodings and bounded cosmetic interest/update work in [replication](../../game/src/multiplayer/replication.ts) and [reference hosting](../../game/src/multiplayer/referenceServer.ts), while preserving nearby gameplay outcomes and private-state filtering. Repeat the full sustained suite after fixes; these earlier flat-pad workloads do not certify the final authored world or full combat mix.

3. **High: a quick first paint hides a long startup.** The first production run painted at 252 ms, but exposed the multiplayer controls at **21.15 seconds**. This readiness condition is later than or equal to game initialization; it must not be labeled time to first playable without the game's own telemetry. By that point the browser recorded 230 resource entries and **95.2 MB transferred** from local preview. Individual main-thread long tasks reached **5.95 seconds**, **3.20 seconds**, and **2.22 seconds**. The largest recorded assets include altar ruins site (9.41 MB), altar (8.12 MB), wand (5.29 MB), and scarecrow (4.77 MB). The repeat captured the game's own first-playable mark at **19.76 seconds** and controls at 19.91 seconds. Its major named spans were navigation construction **6.03 s**, initial scatter **3.26 s**, the first-frame span **3.24 s**, and terrain construction **2.60 s**. These elapsed spans are not GPU timings. Prioritize prebuilt or cached navigation keyed by content/seed, worker-based construction, and attribution of the first-frame stall in [boot](../../game/src/app/boot.ts:757). Then audit the critical preload set and stage optional models by actual visual need. Large local asset transfers are a deployment concern, but the measured six-second navigation block is stronger evidence for the current local startup bottleneck. Loopback transfer times do not model a deployed connection, and compression/CDN behavior was not tested.

4. **Medium: background scatter generation competes with gameplay after readiness.** Source profiles show `collectField` consuming approximately 12–14% of the early offline/empty-online sample and about 5% in the later crowd sample. This is ongoing generation during the observation window, not proof of permanent steady-state overhead. Production profiles independently show `densityAt` as a hot function. See [scatter generation](../../game/src/world/scatter.ts:2043), [streaming scheduler](../../game/src/world/scatterStreaming.ts), and [post-start scheduling](../../game/src/app/boot.ts:3031). In the unclustered candidate loop, rejected points `continue` before the periodic yield check; a rejection-heavy batch can therefore skip those yields. Put cooperative time-budget checks on every path or move deterministic generation off the render thread. Compare the first minute of play and a fully settled scene separately, including movement into newly streamed terrain.

5. **Medium: replicated updates rebuild the visual selection too broadly.** [Browser session update application](../../game/src/multiplayer/browserSession.ts:104) reloads the entity store and calls `views.sync()` for each update, even when most world entities are unchanged. That leads through active-set replacement, selection and reconciliation. Production update application accounts for about 4.7% of the crowd sample; the source run records 6.5%. It is measurable but smaller than rendering. Apply membership/state deltas, retain stable entity references, and route pure position changes through interpolation. Verify world switching, removals and late-session rejection after changing this path. Do not infer that the nearest-player sort is the main bottleneck; the profiles do not support that conclusion.

6. **Medium: full snapshots and durable serialization are a substantial server cost.** In the earlier distributed run, snapshot and commit stages together account for approximately 50% of stage time. [Headless snapshots](../../game/src/multiplayer/headlessWorld.ts:134) clone shared state and entity lists and collect every resident player's private state; [SQLite commits](../../game/src/multiplayer/sqliteStorage.ts:61) serialize world metadata and player records before checking cached values. Use dirty records and transactional deltas or a journal with checkpoints. Preserve acknowledgement-after-durable-commit and restart recovery; delaying persistence without redesigning that guarantee would change correctness. Stage totals include setup, so percentages diagnose broad cost rather than exact sustained per-tick costs.

Server evidence: [distributed report](../../test-results/multiplayer-capacity/distributed-1788713365796/report.json), fingerprint `2201b61c9547accba9e6aa10a3ab8b72994b6d6d544b57495498a54a4a4d904e`; [clustered report](../../test-results/multiplayer-capacity/clustered-1788715002979/report.json), fingerprint `b462c84a5693a3d37228f2d0e6782da26e8e540ba8542c12742a9ae4151aacb2`. Peak server RSS was 1.20 GB distributed and 1.50 GB clustered. The load generator and server shared this machine. No new server-capacity claim is made by this audit.

**Scope and validation**

CPU profiles were collected in separate windows from frame sampling. Six seconds were requested per profile; actual capture windows were longer under load, and stack percentages use the recorded profile duration. Development profiles identify functions but are not substituted for production frame measurements. A single camera and powerful desktop cannot establish laptop/mobile performance. No real-user INP, field Core Web Vitals, GPU execution trace, deployed cache/security-header audit, or long-duration client leak test was collected. Deferred streaming remains active during these early-play measurements. Type checking passes for the audit tool. Gameplay source was not changed.
