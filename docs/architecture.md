# Minimal architecture

The repository has three independent parts:

- `game/` becomes a normal Vite game after a PRD is approved. It never imports run or agent tooling.
- `tools/` starts that game, drives Chromium, calls `window.__gameDebug`, and writes evidence.
- `runs/<run-id>/` holds durable planning and review artifacts for one build.

The root agent owns architecture, shared contracts, integration, and acceptance. A fresh PRD agent proposes only the systems required by the brief. The root removes poor scope, creates the foundation, freezes the smallest useful interfaces, and boots the production-backed feature lab before assigning feature files to specialists.

```text
brief -> fresh PRD -> root review -> browser foundation -> frozen contracts
      -> lab fixture + owned feature round -> lab state + screenshots
      -> root lab acceptance -> final-world wiring -> shallow smoke
      -> fresh critic -> fix in lab -> accept -> reintegrate
```

The foundation is real code, not stubs: application boot, renderer, scene, update loop, input, Rapier, Recast, asset loading, canonical state, shared types, debug API, and Playwright connectivity. It must launch successfully in Chromium before parallel game work begins.

The feature lab uses those production paths in a compact deterministic scene. An isolatable feature is built and accepted there before the root wires it into authored final-world content. If the lab cannot prove a feature yet, the first task extends the lab. Only behavior whose subject is the authored full world can skip this gate, and the task must record why isolation would invalidate the test.

Shared contracts normally live in `game/src/contracts.ts`, but their contents come from the approved PRD. The template does not predeclare final-game schemas. When a contract is wrong, specialists stop; the root updates the contract and affected callers together.

The game server runs the production simulation without the renderer. It boots the authored world from a baked server world pack that holds terrain heights, solids, the navmesh and the tree scatter as plain data, and it builds entities and creature placement from its live catalog at every boot. Code that needs three or GLB files to produce that pack lives in `game/src/multiplayer/bake/`, and a test keeps it out of the server's module graph. See [Server world pack](./world-authoring.md#server-world-pack).

The server is two layers. `game/src/multiplayer/worldHost.ts` is the host core: hosted worlds, peers, the join (authentication, the admission hook, the player lease), command intake with receipts, the tick loop (commands, simulation, snapshot, commit, acknowledgements, replication), the `betweenTicks` hold that a publish and a player edit run in, eviction, and the final commit that frees every account. It talks to a peer through a `PeerLink` that carries message objects, takes its storage, authentication, admission hook, catalog revision, log and timers as options, and imports nothing from Node; `tests/world-host-import-graph.test.ts` holds it to that. `game/src/multiplayer/referenceServer.ts` is the network server around it: the HTTP routes, the WebSocket adapter (JSON framing, the message size limit, the Origin check, the authentication deadline, outbound backlog and byte accounting, ping and the silent-peer timeout), bans, administration, publishing, settings and the directory heartbeat. The core is written to run behind a MessagePort link in a Web Worker as well, which is how local play will host it; `tests/multiplayer-world-host.test.ts` runs it over an in-memory link with no socket. Per-world state lives on one `HostedWorld` and refers to no sibling world, so a host with one world is the unit a later world-per-thread server runs.

Local play keeps its world in IndexedDB. `game/src/multiplayer/indexedDbStorage.ts` is that same in-memory storage with write-behind persistence through a small key-value port: a commit applies in memory and marks the rows it changed, and a timer writes every marked row about every five seconds — and on `close()` — as one batch, which is one IndexedDB transaction. The host commits ten times a second, so a commit that waited for the database would put a database round trip inside the tick loop. Five object stores hold whole rows: `meta` (the schema version and the catalog revision last written), `worlds` (one row per world, without its entities), `entities` (one row per entity, so a tick that moves one creature writes one row instead of the seed-1337 world's 18,859), `players` (one character row per account) and `worldPlayers` (what one account owns in one world, with its receipts and its random cursor). Opening a world writes the whole entity baseline once, about 9 MB for the shipped world and dominated by landmarks and creatures; every flush after that is a few kilobytes.

Every marked row holds the value as of the commit that marked it, and a batch holds every row marked since the last successful flush, so a batch is always a consistent cut of the world. A tab killed between flushes loses at most five seconds of play and never comes back to a torn state, such as an item both on the ground and in the inventory. A flush that fails — quota, blocked, aborted — keeps its rows dirty, retries with a backoff and reports through the `onError` option so the UI can warn; after five consecutive failures the store stops retrying and play continues in memory. Leases are never stored, so a tab that died leaves no account claimed. Two tabs must not share one store: the opener holds a Web Lock for the database, and a second opener fails with `LocalPlayBusyError` ("Local play is already open in another tab") rather than writing over the first.

The old single-record save, `localStorage["corealm.save.v1"]`, is imported once by `game/src/persistence/localSaveMigration.ts`. The main thread runs it through the game's own load pipeline and hands the worker a character row and an owned-world row; no world record is written, because the old client's node, creature and loot-pile ids are not the server's spawn ids. Ground loot and respawn timers are dropped by design, position is kept, and skills, quests, discovery, inventory, bank, equipment and currency carry over exactly. The raw text is copied to `corealm.save.v1.backup` before anything reads it, once and never overwritten, including when the save turns out to be corrupt. `corealm.save.v1.migrated` is set only after the worker acknowledges the import, so an interrupted import repeats instead of losing a save, and settings stay in localStorage where the main thread reads them.

### Local play in a worker

"Play local" is a world like any other: the host core runs in a Web Worker and the page joins it as a session. There is no other local game: the page has no simulation to fall back on. `?local=memory` runs the worker with nothing stored. `window.__gameDebug` reaches the worker's world through a debug channel that exists only on the local MessagePort link (`worker/localDebugProtocol.ts`, `worker/localDebug.ts`): the host applies an operation between ticks, replicates, and only then answers, so the page shows the effect before the promise resolves. A socket has no such message, and the host core refuses one as unknown.

The client half of the protocol is `game/src/multiplayer/sessionClient.ts`. `joinWorldSession` sends the join, checks the `joined` reply against the chosen world, waits for the first snapshot and replays unacknowledged commands; `ClientWorldSession` handles commands, acknowledgements, updates, content-updated and errors. It talks to a `SessionTransport`, the mirror of the host's `PeerLink`. `webSocketProvider.ts` supplies one over a socket: JSON frames under the size limit, a five second wait for the join and for each acknowledgement. `messagePortLink.ts` supplies one over a MessagePort, and the host's `PeerLink` for the other end: structured clone instead of JSON, no acknowledgement timeout because a port cannot drop a message, and a close frame because a port has no close event a page can rely on. Both providers call `joinWorldSession` and nothing else speaks the protocol, so connected and local play are one session code path.

A local world's descriptor has the endpoint `local:worker`, which is not a URL. `descriptor()` in `protocol.ts` accepts it only from the page's own code. Everything remote (a directory, a `/worlds` reply, a socket's `joined` message) is parsed with `descriptor(value, "socket")`, which still demands an encrypted or loopback `ws(s):` endpoint, so no server can name the page's worker as its address.

`game/src/worker/localHost.ts` is the worker entry, and it keeps the install-before-import rule. Its static imports are `catalogInstall.ts`, `localHostProtocol.ts` and the contracts, none of which evaluates a content table. On `start` it fetches `generated/local-world.json`, then the server catalog and the world pack that manifest names, calls `installCatalog`, and only then `import()`s `localHostRuntime.ts`, whose graph is the host core, the world pack loader, the lab world and the systems. `tests/local-worker-import-graph.test.ts` holds the worker to four things: no renderer, GLB reader or UI, nothing from Node, no bundled catalog, and no content reachable statically from the entry. The build's budget plugin also fails if a worker file carries catalog tables.

`localHostRuntime.ts` creates the same `createWorldHost` a server runs, over `createPackedWorld(pack, seed)` or the lab world, with `openLocalWorldStorage()` and an authentication adapter that answers every token with the one local account, `local:player`. A seed the pack does not hold falls back to the pack's first seed; `multiplayer/localLaunch.ts` settles that on the page from the same manifest before the scene is built, because the scene and the worker's world must be one seed. An old save is imported only when the store has no character for the local account: it joins through `HeadlessWorld.join` the way a player arriving from another world does, so a save from an unpacked seed keeps what it carries and starts at the safe spawn, and it is committed and released before anyone connects. The worker then reports `imported` or `existing`, and only then does the page call `markLegacySaveMigrated`.

A feature lab is the same worker with the `lab` fixture. `start` carries a `LabFixtureSpec`, read from the URL by `featureLab/labSpec.ts`, and the worker then waits for one `lab-world` message before it builds anything: `worker/labWorld.ts` makes the `HeadlessWorldPorts` from the spec and from the `LabWorldData` the page sends once its scene is drawn (terrain sampler, baked navmesh, solids, entities, trees). Both are validated at the worker boundary (`parseLabFixtureSpec`, `labWorldData`), and both modules import only contracts and types, so the entry still evaluates no content before the catalog is installed. A lab never opens IndexedDB. The `lab.*` operations of `worker/labProtocol.ts` ride the debug channel and are applied by `worker/labDebug.ts` between ticks. The lab page runs no simulation; `featureLab/runtime.ts` is a client of those operations. [The lab reference](./lab-reference.md#how-a-lab-runs) lists the messages.

`WorkerWorldProvider` (`multiplayer/workerProvider.ts`) lists the one local world, needs no login, and owns the worker. The worker starts as soon as local play is known to be the target (`?play=local`, or "Play local" picked while the scene loads), so its world boots beside the scene, and `connect` hands it a MessagePort. The worker's own channel carries what a server does with a process and a disk: `start`, `connect`, `catalog` (the session's `SessionCatalog.load()` asks the worker for `clientCatalog()` of its installed tables, where a socket session fetches `GET /catalog/<revision>`), `flush` and `close`, and back `ready` with timings, `failed`, and `storage-error`. The page forwards `visibilitychange` to hidden and `pagehide` as `flush`, since a worker hears neither. Closing the session saves the character, flushes and closes the store, and ends the worker, which also frees the store for another tab. A worker that dies ends its session; the controller's rejoin is refused once with "Local play stopped unexpectedly", and choosing Play local again starts a new worker. A store held by another tab refuses the start with that reason on the picker's status line.

The page is a thin client in every mode. `GameLoop` (`app/loop.ts`) reads input and draws: it has no simulation tick, no system list and no save. `CorealmGameApi` is built on the page as a replica (`{ replica: true }`): reads answer from the replicated store, every write is a command `submit()` hands to the joined session, and the synchronous write methods refuse. The same class without that flag is the executor a host runs each player's commands through (`multiplayer/headlessPlayer.ts`). What boot still constructs beside rendering, input and UI is what those reads need: `Movement`, `Navigation` and `Solids` for movement prediction, and the read-side view computers behind the API's hooks (bank and shop listings, quest summaries, hunt contracts, each verb's reach), built over an event bus with simulation listeners switched off. Between sessions the store holds a blank character at the spawn and the scene shows scenery only.

The authored game page draws its world from the baked records on the asset host. From `assembly/semantic` it keeps static scenery, solids, buildings, known locations, the route graph, the portal mouths and the dungeon; creatures, characters, resource nodes and doors arrive only by replication, and the baked ones near the spawn are used once, as a list of models to preload. From `spawns/world` it reads where creatures stand and the habitats as they were spread, for the two things it draws from them: habitat dressing, and the trees scatter leaves out of creature corridors (`readBakedMobSpawns` in `world/mobSpawnCache.ts`). A lab page, the world bake and the map capture still assemble a world on the page, because a lab describes its world to the lab worker and the bake writes those records.

The entry, `game/src/main.ts`, evaluates no content. It fetches `generated/local-world.json` and the catalog that manifest names, calls `installCatalog`, and only then imports the app (`content/catalogEntry.ts`). The game page installs the client projection, `generated/client-catalog-<hash>.json`: item, recipe, spell, shop and quest-log tables, region geometry, and creature rows cut down to model, scale, name, family and tier. Loot rolls, combat and AI numbers, habitats, encounters and placements are not in it, and `content/worldData.ts` builds an unpopulated world from `regions` when the catalog has no `world` table. A joined server's revision is laid over it and removed on leaving (`content/clientCatalogOverlay.ts`). Lab, bake and capture pages install the full catalog the manifest names for the worker, fetched and never bundled. A failed fetch leaves the boot screen with the reason and a Retry button. `tests/client-catalog-page-graph.test.ts` walks the page's module graph (`tools/lib/page-graph.ts`), requires the entry's static imports to be content-free, evaluates every content module the page can load against a client-only catalog, and fails with the module, the table and the import chain when the page reads something the projection lacks. The build's budget plugin fails if a page script carries loot rolls, habitats or the compiled catalog.

`tools/local-worker-test.ts` proves the whole local path in a browser, including the import of an old save, against the dev server or, with `--dist`, the production build.

The build publishes what the page and the worker fetch (`tools/lib/local-world-files.ts`): `generated/local-world.json`, fetched with `no-cache`; `generated/client-catalog-<hash of its bytes>.json`, the client projection the game page installs; `generated/server-catalog-<hash of its bytes>.json`, the whole compiled catalog with `formulaRevision`; and `generated/server-world.pack`, fetched as `?v=<pack revision>`. The large files can be cached for good, and a new build never pairs a worker with a stale catalog or pack. The dev server answers the same URLs from the compiled catalog on disk. The worker is a module worker in its own bundle under `assets/worker/`, with its own gzip budget in `game/vite.config.ts`, and it shares the page's one recast `.wasm` file.

Use the commands in [the development loop](./feature-lab.md). Browser checks and the persistent session call production paths directly; there is no separate agent command dispatcher.
